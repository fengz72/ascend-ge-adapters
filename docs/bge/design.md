## 3. 输入、输出与参考

ONNX 为动态接口，包含 3137 个节点、400 个 initializer。本轮支持和验收范围收敛到提供的五条样例及其重复、重排和并发，不从动态符号推导任意 shape 都已受支持。

| 输入/输出 | dtype | 图接口 | 本轮范围 |
|---|---|---|---|
| input_ids、attention_mask | INT64 | `[B,S]` | B=1，S 为 6/9/8/13/8；mask 为 0/1，有效维度一致 |
| long_cid3_raw、long_action、long_time_bucket | INT64 | `[B,L]` | B=1，L=128，三者维度一致 |
| stat_dense_raw | INT64 | `[B,20]` | 按提供样例，合法索引由原样例固定 |
| stat_ratio | FP32 | `[B,20]` | 有限数值，保持原始值 |
| stat_count | INT64 | `[B]` | 0～20，沿用样例 |
| scores | FP32 | `[B,10112]` | 每请求完整输出到 Host；不只回传 Top10 |

输入为每请求 3416～3528 字节，输出为 40448 字节。数据量小只构成分析线索，不能据此宣称瓶颈或收益。样例只有四种文本 shape、一个行为长度；未覆盖 B>1、其他文本/行为长度、空输入和越界输入的设备语义。框架现有无效输入检查另作 CPU 回归，不把异常输入结果混入正常性能分布。

参考独立于候选：使用原始模型的 CPU ONNX Runtime 完整分数，以及用户提供的 expected Top10。CPU golden 绑定模型/输入/ORT 版本和配置；历史 golden 身份不充分时重建，不由候选生成 expected。

完整分数门槛保持 cosine≥0.9999、relative L2≤0.001、max absolute error≤0.001。Top10 的 `dense_id=输出下标+1`，ID 和顺序精确一致，分数 atol=0.001、rtol=0；同分采用稳定下标顺序。NaN/Inf、输出数量或 shape/dtype 错误直接失败，不改阈值或 expected 来通过。

## 5. 功能、精度、压力与稳定性

| 阶段 | 执行与通过条件 |
|---|---|
| 离线回归 | 相关 Python/C++ 契约通过，配置生效、原图/材料身份一致；本轮设计审查不冒充重新运行回归 |
| 新设备正确性 | 修正后的全核单实例先运行五例，完整 CPU 分数和 50 个 Top10 项全部通过，再建立性能基线 |
| 候选门禁 | 每个核/实例组合先以专门压力轮次核对五例的完整输出，任何错误、串数据或精度失败均不进入收益判定 |
| 最终压力 | 冻结配置，至少 2000 请求，保证每实例每个 case 至少出现 20 次；覆盖重复、交错和四种文本 shape 切换，按请求关联完整分数与 Top10，不仅核对调用数 |
| 生命周期 | 在允许的接口下完成三轮加载→混合请求→销毁；记录本任务进程退出、锁与设备上下文释放。错误/超时清理先以 CPU stub 测，再按真实接口做受控设备验证 |
| 稳定性 | 最终配置连续 10 分钟，0 错误/超时/丢失/重复响应；记录每 10 秒 Host RSS、HBM 与成功吞吐，确认资源平台期和退出后释放 |

稳定性在预热后计时，前/后各两分钟资源中位数比较：RSS 增量不超过 max(128MiB,初值5%)，HBM 增量不超过 max(64MiB,初值1%)，并检查连续增长趋势；超限先分析缓存或其他负载，不直接写“泄漏”或“通过”。设备受外部任务干扰、状态无法确认或预算不足时，相应项目写未验收，不用历史单实例 PASS 代替最终多实例证据。

本轮性能区分两个场景，使用独立场景ID、实际请求池、基线和性能run；输入身份见[双场景契约](evidence/20261026/workload-contract-v2.json)。

|场景|实际回放负载|用途与当前状态|
|---|---|---|
|fixed-case-0002|仅`case-0002`，B1/S8/L128/stat20，重复完全相同的八输入|默认调优对照；取原始顺序中首个中位长度S8样例，未按速度选择；尚未实测|
|random-five|case-0000至case-0004，等概率0.2、有放回，全局请求索引配种子|原有所有性能数值所属场景；作为最终多case性能与混合shape验收|

- 请求定义：两场景均B=1，每实例最多一个在途请求，闭环饱和施压，下一请求在前一完整输出就绪后发送。固定case池必须实际只有一条；随机池实际五条。保存每请求case_id和场景/计划身份；不能由随机日志的case-0002分组时延推算固定场景QPS。报告各场景总体样本数、成功率、吞吐、p50/p99；随机另列分case统计，不称为服务端排队容量。
- 计时起止：Host 输入已备好，首次 H2D 前取单调时钟；包含描述符、全部输入搬运、GE 完成同步和完整 scores D2H；Host 输出可安全读取后取结束时间。文件读取、分词、CPU 参考和报告落盘在外；服务网络、排队与批处理等待不在本轮范围。
- 缓存：原始五输入可预装 Host 内存，模型/权重常驻；每请求仍执行真实 H2D、GE、D2H，不使用结果缓存或设备输入命中代替执行。每实例对当前场景参与的每个case预热至少10次，预热包含D2H；固定性能覆盖该一条，随机性能及全量压力覆盖全部五条内容和四种shape；编译、加载和预定预热不计性能，但计设备占用预算。测量内新编译或未命中保留耗时。
- 窗口：两场景分别计数，搜索每配置每场景至少30秒且至少2000请求；正式基线和冻结后验收每场景每轮至少60秒且至少10000请求，各三轮。测量分别最多 180/300 秒；达到时间上限仍不足请求门槛时标为统计不足，不能降低门槛冒充验收。
- 完成统计：保存同一时钟的测量窗口起止、请求开始/结束、case/instance/request_id、状态和分项。主 QPS=`窗口内成功完成的请求数÷窗口实际秒数`；窗口截止后停止新发请求并排空，同时报告退出时在途数、完整请求延迟和排空时长，不把排空后的请求总数除以发送窗口冒充稳态容量。
- p99：固定/随机分别统计，不合并两场景延迟；最近秩 `sorted[ceil(0.99*N)-1]`，总体与分 case 分开，错误/超时不能静默剔除。跨轮同时保留各轮值和合并原始延迟分布；不平均 p99。无 p99 上限，结论中只报告观察值。
- 有效性：0 错误/超时、0 未归档请求；闭环并发有界、结束全部排空，10 秒窗口吞吐无持续下降，Host 发生器无明显饥饿。外部设备任务、Host 构建争抢或 profiling 使轮次不可比时判无效。profiling 独立采集，不计入正式收益。
- 波动：正式收益采用独立验收三轮吞吐中位数，合并 p99 另列。吞吐提升不足 3%，或不超过基线/候选轮间相对极差中的较大值，记录观测差值并判“无显著变化”。按预算交错复测消除漂移，不无限追加轮次。

## 8. 预算、交付与恢复

保守执行含基线最多 12 组唯一配置，复测不新增配置名额但计入占用时长。累计设备占用上限 7200 秒，包含设备编译/加载、预热、正确性、无效/失败轮次、profiling、复测、压力与稳定性；等待空闲及离线设计不计占用。主控逐任务登记实际锁持有及设备开始/结束，预算余额不足以完成下一任务时不启动。

至少预留50分钟且不低于新增双场景验收所需估算值：固定/随机×基线/最终×三轮共12个正式run，按已测编译加载/吞吐估算，加全五例压力、随机场景10分钟稳定性、清理及20%余量。原单场景预留推导为：六轮测量若各达 300 秒，加上 10 分钟稳定性已需 40 分钟，另需加载和压力余量。根据实测加载/完成速率动态估算全部剩余验收任务，增加 20% 余量；估计高于预留时提前停止搜索并提高预留。仍不足则保持未验收，不压缩已冻结的门槛。单个设备任务一般 timeout≤600 秒，10 分钟稳定性含加载可设≤900 秒且受总预算约束。仅外部干扰/可确认的基础设施失败允许同配置重试一次并计预算；正确性失败立即停该候选，内存不足/两次同类失败停止向更高并发探索。两轮细调无超过波动的收益即停止；不要求耗尽 12 组。
