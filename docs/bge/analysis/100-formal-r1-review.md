# 100 正式第一轮：Host、NPU 占用与长尾离线审查

结论：**可以继续收集冻结配置的既定三轮，但目前不足以最终接纳首轮随机八实例的性能结果。** 没有看到请求错误、任务失败或采样点中额外 NPU PID；`final-best-random-r1` 同时出现较高宿主 CPU 忙碌和更大长尾，需要补充归属与时间关联证据。不能仅凭全局 CPU 百分比判为外部干扰，也不能因检查器写 `formal_round` 就认定环境可比性已完成验收。

本审查只读取本地主控已归档的摘要、检查器 stdout 和采样实现，没有连接100、启动设备任务、运行远端 CPU 分析或修改进行中的第二轮。没有读取100原始 resources/events，因此本报告不冒充对原始事件的再次独立统计验收。

四个作业的现有输出均记录 exit=0、0请求错误，身份/输入和单轮事件检查通过，实际窗口 ≥60 秒且完成 ≥10000 请求。随机八实例窗口完成35014、cohort完成35021，尾部排空6.889209ms；固定八实例窗口36345、cohort36352，排空6.944971ms。窗口外完成的7个请求已被排空并保留延迟，不等于丢失响应。

fixed与random是不同输入场景，随机中包含更长文本和shape切换；两者p99差值不是同负载的退化幅度。单轮也不能证明同场景的轮间p99波动，必须保留case组成与并发调度的解释空间。

随机八实例的分项 p99 为 execute+sync 23.633682ms、H2D 0.438ms、D2H 0.189502ms。较高尾延迟出现在包含 GE 执行和同步的阶段，但该阶段也包含 Host 发起、调度与等待。**不同分项的 p99 不能相加或直接相减归因，现有摘要也不能定位235.8ms那个请求的具体阶段。**

## 现有采样能证实和不能证实的内容

| 证据 | 可以支持 | 不能据此确认 |
|---|---|---|
| NPU PID | 每个窗口采样点中目标芯片仅一个固定PID，同卡另一芯片均没有PID。分别为1986884、2027888、2080876、2111693 | 整个窗口没有短暂外部任务；这些宿主PID已经直接映射到本任务container runtime；Host或其他共享资源没有争抢 |
| 作业与门禁 | 四个作业退出0、现有身份checker通过。按当前guarded实现，前后gate没有拒绝任务 | 测试角色已经重读并核对四份原始before/after gate的物理身份和时间；门禁之间始终独占。最终仍核原始gate JSON |
| Host CPU busy | 随机八实例的全机平均忙碌采样显著高于另外三轮 | 本任务实际使用的核已饱和、出现CPU配额节流，或一定是外部进程造成。也可能包含GE自身混合shape的Host开销 |
| p99与最大值 | 随机八实例长尾明显高于本轮固定八实例；原始观察必须保留 | 长尾与CPU高负载已在时间上对应；确定为NPU kernel退化或外部Host干扰；235.8ms代表常态 |
| 资源样本数 | 本轮每窗口仅4～6次实际观察，随机八实例最稀疏 | 约10秒采样间隔覆盖完整、采样未延迟、是否存在中间缺口。需要原始时间戳与命令时长 |

当前采样实现见 [run_runtime.py](../../../delivery/supporting-evidence/work/bge-opt-100/legacy-tools/run_runtime.py)：CPU busy 来自相邻两次 `/proc/stat` 的全机 tick 差分，扣除 idle/iowait，未分开报告 steal；它是一个区间平均值，而不是当前时刻或单个请求的CPU占用。第一个落在测量窗口内的区间可能包含预热/加载尾部。采样先读取Host信息，再调用 `npu-smi`，完成后等待10秒，因此实际间隔可能大于10秒。没有原始时间戳时，不能把64.5%直接对齐到第一个十秒请求桶。

## 吞吐时间桶的两个注意点

随机八实例的完整六个十秒桶约为571.4、550.1、596.5、591.3、594.4、597.6 QPS；早段较低，后段恢复。固定八实例六桶约605.3～606.0 QPS，比较平稳。单实例两场景也呈现前段偏低、后段上升，不能仅依据随机八实例的一次异常就宣布原因。

主控 `inspect_formal.py` 将最后不足10秒的尾桶也除以10，摘要中的最后 `0.1 QPS` 不是吞吐塌陷。正式复核必须用桶实际时长、窗口内完成数；已准备的tester入口保留部分桶真实时长。它不能用来证明10分钟稳定性失败或持续下降。

## 最小补充证据

1. **归档已有原始证据，测量结束后再离线关联。** 四个run的 `resources.jsonl`、`events.jsonl`、`requests.csv`、before/after gate、job request/status、实际plan及结果；保留原始单调时钟窗口起止和SHA。先定位超过本轮p99的请求及最大请求，按 case、instance、H2D/execute+sync/D2H 与资源采样区间对齐；若已有 first_hit/编译标记，也核对窗口内是否出现新编译。无需重新跑CPU reference或启动profiling。
2. **同次运行的进程归属与CPU区间增量。** 以已记录的runtime container PID和 `npu-smi` 宿主PID做一次明确映射，并在同一时钟下保留本任务进程/必要线程的 user/system CPU 增量、可运行状态和上下文切换，以及主要其他高CPU进程的身份和增量。这样才能区分“GE自身Host开销”和“外部CPU争抢”。只记录进程名或全机load average不足以完成归因。
3. **实际CPU资源约束与节流。** 一次性保存runtime的允许CPU集合/NUMA、cgroup CPU配额与cpuset；同区间保留相应核的busy/steal、运行队列和cgroup节流计数增量。全机尚有空闲不代表本任务亲和核或配额有余量。采样只需轻量只读，不改变正在运行任务的亲和、核数、实例数、预热或计时契约。

对于已经结束的第一轮，无法补造当时的进程/线程CPU快照；缺口如实保留。第二轮正在运行时不要修改其测量实现；可由主控在已有授权范围内保留独立轻量只读见证。每项补采需要带时间与进程身份，不需要加入大规模CPU扫描或新设备任务。

## 对继续验收的建议

- 保持已经冻结的模型、核数、实例、输入分布与计时范围，保留第一轮全部结果，继续既定交错顺序采集；不因一轮较慢就删点或选择最好三轮。
- 首轮随机八实例标记“事件/统计契约通过，环境与长尾归因待复核”。高CPU本身不是预先定义的无效门槛，不能临时以某个百分比宣布失败或自动重跑。
- 三轮后先比较各场景的轮间波动，再结合上述同次证据决定是否具备正式收益声明。若确认外部干扰或基础设施故障，按原预算/同配置重试规则处置并保留无效原因；若无法确认归因，报告所测Host条件及p99风险，不宣称已经解释或排除干扰。
- p99没有硬上限，不能将24.1ms或235.8ms单独判为SLA失败；也不能因为吞吐提升明显而省略尾延迟和资源证据。最终仍需三轮原始独立复核、混合shape压力与≥600秒资源稳定性。

## 第二轮补充的PID归属见证

主控新增同次 [docker top快照](../../../delivery/supporting-evidence/work/bge-opt-100/host-pid-snapshot-r2.txt) 和 [NPU进程快照](../../../delivery/supporting-evidence/work/bge-opt-100/npu-smi-r2.txt)。前者时间为2026-10-26 22:19:47 UTC+8，显示 `final-best-random-r2` 的device_job→guarded→run_runtime调用链，native宿主PID为2478386；后者目标NPU1/Chip0的唯一PID同为2478386，Chip1无进程。这直接补强了该时点目标NPU PID属于本任务的证据。

该见证仅对应第二轮一个时点，不能回填第一轮PID归属，也不能证明整轮无短暂外部负载。快照中的native `%CPU=133` 是ps口径，不能当作同区间每核饥饿或与第一轮全机CPU忙碌直接相减。NPU文本前缀还含 `dcmi initialize failed` 等错误而后续打印了进程信息；最终应结合原命令与退出码及常规resources采样明确该片段的适用范围，不把整条混合输出无条件当作全部查询成功。
