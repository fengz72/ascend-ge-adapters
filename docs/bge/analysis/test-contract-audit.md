## 必要的最小 runner 改动设计

以下是后续开发建议，本轮不实施，也不登记虚构的性能收益。

1. **补齐输出就绪钩子。** 在共用 `PoolResources` 或 GE 专用等价路径增加读取输出步骤，每次请求在 execute+sync 成功后，检查实际输出 dtype/shape/有效字节数，将完整输出拷贝到该实例独占的 host 缓冲；拷贝成功才记完成。计时为 `t0`（H2D 前）→ `t3`（D2H 返回且 host 输出就绪），分别保留 H2D、desc、execute+sync、D2H 和 total。失败 D2H 属于失败请求。benchmark 不调用当前会输出逐张量 INFO 和构建临时 vector 的重型 capture 逻辑。
2. **控制 host 缓冲生命周期。** 每实例拥有独立 host 输出缓冲，按实际容量安全复用，预热覆盖全部四种 shape 及输出路径。容量不足时的分配若发生在正式请求里必须保留在该请求计时内。当前输出是连续 FP32 `[1,10112]`，有效数据为 40,448 字节；仍根据实际 runtime 输出校验，不能盲拷贝容量或让地址变更漏读。禁止跳过输出搬运、只拷贝 Top10、或让下一次执行覆盖尚未读取的输出。
3. **归档实际请求终态。** 每轮冻结唯一 run ID、代码/图/配置/数据身份、seed 和计划请求数。记录 `request_id`、全局 ordinal、instance、input_set、shape_key、phase、status、同一 `steady_clock` 下 `sent_ns`/`received_ns`/`completed_ns`、各段时间及错误阶段。闭环没有开放到达计划；不要虚构发送计划或排队时长。日志落盘、JSON 序列化、Top10/CPU 比较放在正式性能边界外，并用同一策略计入统一 wall 或在另一个线程可靠收集，不能使记录损失不可见。
4. **支持独立压力采集。** 在与性能相同实例/stream/buffer 路径上运行单独压力轮次，为每次请求保存唯一 ID 及对应的 case、实例、实际输出与数值检查结果。可顺序写二进制与 sidecar 索引，或在压力路径当场与预加载 CPU 向量比较并保留错误输出；不能只保留最后一次输出或按 case 字典覆盖重复请求。压力轮次不计为性能测量。
5. **固定统计规则与失败语义。** 输出明确 `arrival_model=closed_loop`、`inflight_per_instance=1`、`latency_scope=h2d_desc_execute_sync_d2h_host_ready`。p99 用最近秩，汇总原始请求而非平均各轮 p99。失败/超时、缺失/重复/未终态请求使该轮无效；即使报告成功子集诊断值，也不能写为通过。p99 上限缺失时显示 `not_configured`，报告观测 p99 与吞吐，不调用必须带有限 p99 上限的辅助脚本伪造 SLO 通过。

只需服务于选定 GE 路线的最小能力，不为当前任务引入服务框架、开放到达系统或异步多在途。若未来改变 batch/异步并发，则另补这些范围的参考与压力契约。

## 可离线验证的回归测试

这些测试后续可在 CPU 上执行，不依赖空闲 NPU；本审查没有执行它们。

| 测试 | 有意义的断言 |
|---|---|
| 输出完成边界 | fake backend 的 execute 标记 device-ready，collect 将不同输入签名写到 host 并延迟；请求结束时间必须在 collect 完成之后，collect 次数等于成功执行次数。用可注入时钟或有界同步事件判顺序，避免只靠脆弱的 sleep 差值 |
| 输出读取失败 | H2D、execute、D2H 分别失败，记录错误阶段；失败 D2H 不能产生 success。明确未执行请求、保留已完成记录，退出失败且资源只释放一次 |
| 请求记录完整 | 多实例、不能整除的请求数、重复 case、相同 shape 不同内容：ID 唯一、全局抽样序列与 seed 可复现、各计划请求都有终态或明确未执行原因，不因 instance 分组覆盖 |
| 独占缓冲 | fake backend 为不同实例/请求写不同签名，验证 host 缓冲不跨实例共享，下一请求不会改变已保存或已比较的响应；注入交换/旧输出必须被压力比较检出 |
| 统计边界 | 1、2、100、200 个已知延迟的最近秩 p99；多轮聚合不能平均 p99；重复/缺失/pending、负耗时、时间逆序、NaN、失败记录应拒绝有效性能结论 |
| 精度门槛 | 沿用业务测试，补多实例重复请求关联；注入 ID+1 错误、Top10 同集合错顺序、相同 shape 错 case、超阈值/NaN，应各自失败。输出 shape/dtype 精确检查单独断言 |
| 生命周期与日志 | setup 部分失败、预热失败、工作线程异常与读取输出异常不死锁；无设备所有权时不启动 runner，取消仅终止本任务；写日志失败不能当吞吐成功 |

## 设备可用后的独立验收设计

设备被占用时仅完成文档、只读调查和允许的离线工作。不得为测量先占用别人的设备、先跑后等，或在全忙状态下补做正确性/编译等同样会触发 NPU 的工作。主控在真实主机/容器确认物理设备映射、共享锁与当前负载后才能派发，每个任务有唯一 run 目录和有限时限；以驱动/实际负载及进程核对确认完成，不能把 SSH 退出或 OS 锁释放当作 NPU 释放证明。

建议按以下次序实施，全部计入主控确认的有限预算；到达 12 组或 2 小时先停止，不通过降低样本量改写成验收成功：

1. **可信串行基线。** 冻结新代码身份；原 ONNX 与导出图做结构/权重/IO 等价核查，保留 30 Slice、0 Range 的预期证据并重新记录完整 SHA。在目标全核、单实例、mode=0、FP32 下，对五条样例重新执行，逐条全向量与 Top10 比较。通过后开始性能搜索。
2. **测量预检。** 五条样例等概率、有放回回放；固定 seed 的全局输入序列对所有候选一致，覆盖四种 shape 的预热在同一 worker 内完成且包含 D2H。保留初始化/编译/预热耗时与配置，明确这是热缓存回放；测量中出现额外编译、shape miss 或分配不能事后剔除。profiling 与正式测量分开。
3. **有限搜索。** 先全核/单实例基线，再核数/实例候选。搜索与验收都记录 QPS、total p50/p99/max、D2H、失败和运行时资源；无 p99 上限时按正确性通过的吞吐选择并同时展示尾延迟代价，不能声称满足未知 SLO。核数由实际设备能力核实，不能把历史 `4|8` 当全核。
4. **冻结后独立性能验收。** 建议基线和最终候选各三轮独立 seed，每轮至少 60 秒且至少 10,000 次测量请求；单轮最多 180 秒。若 180 秒内不足 10,000 次，则保留真实数量并标尾延迟证据不足，不能无限延长预算。新 seed 只提供独立顺序，不提供独立业务数据。保存每轮结果与合并分布，分 10 秒窗口检查完成速率与在途数，标出末尾排空；若采用有限请求模式，必须明确其闭环完成速率范围，不能写为开放到达生产容量。差异接近轮间波动时记录无显著变化。若预算不足此方案，应在运行前由主控缩减候选组数并明确未验项目。
5. **最终压力正确性。** 使用最终代码、全局核配置和实例数，至少 10,000 次有唯一请求 ID 的混合顺序回放，每实例都覆盖五 case、同 shape 不同内容、长短 shape 反复切换及重复输入。每次都验证实际 host 输出 dtype/shape、完整向量与业务 Top10；检查遗漏、重复、错实例、串 case。独立 seed 与性能验收分开。故意注入的异常仅限 runner 合法支持的错误路径，不能要求本不支持的取消接口。
6. **稳定性与清理。** 建议最终配置持续 10 分钟，独立监控进程 RSS/HBM、错误与每段完成速率；完成预热后以头尾各两分钟中位数和曲线检查是否仍持续增长。增长需区分动态池平台期、外部进程、采样噪声和真实泄漏，出现持续趋势或 OOM/设备错误则不通过并调查。至少三个合法的启动→混合 shape 执行→正常结束周期，另做一次任务级取消，核对进程与设备状态恢复。10 分钟是有限稳定性观察，不宣称长期 SLA。

本审查建议的样本数/时长是设计输入，尚非已经完成或经用户单独确认的验收结果。主控应在总预算内写入最终设计；预算冲突时保持可追溯地减少搜索范围，不悄悄降低已冻结的验收规则。

## 向工作流内化的约束建议

- 新任务允许显式选择“p99 无硬上限”的探索模式：完整报告尾延迟与吞吐，`SLO acceptance=not configured`，不伪造通过；以后给出上限再复判可行性。
- 设备全忙时，进入“设计完成、设备实验待资源”的明确状态，保留恢复条件，不自动等候或反复抢设备。该前置条件应覆盖所有会触发 NPU 的编译、正确性、profiling 与性能任务。
- “有限预算”必须是候选数/实际任务累计时长等可计数值；核数是调优变量，不是实验预算。累计时长建议包括本任务的 NPU 构建/预热/运行/验收，纯资源等待不消耗设备时长；主控单独记录墙钟进度。
- 设备辅助 OS 锁只协调合作进程；正式测量前后另核真实负载，禁止把逻辑 device ID 或文件锁当物理独占证据。
